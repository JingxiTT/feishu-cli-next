---
name: lark-doc-concise
description: Read, author and edit Feishu Docx or Wiki content and its embedded resources with the official CLI. Route document URLs by path/token, including alternate hostnames. Use Drive for file-level operations or independent comments, and Sheets/Base for embedded data.
---

Use `lark-cli docs` shortcuts for document content. Prefer explicit `--as user`; bot access differs. Creation as bot also attempts `full_access` for the current CLI user. A failed grant does not undo creation or transfer ownership. Read `permission_grant`, warnings and tips separately from the main result. Content read/write/create require the corresponding `docx:document:readonly`, `docx:document:write_only` and `docx:document:create` scopes. Media uses `docs:document.media:upload` or `docs:document.media:download`; resource operations can add read/write/Wiki or export-authorization scopes. Most content/history/media shortcuts support user and bot; Docs search is user-only. Authentication and scopes belong to `lark-shared`; consult it when managing credentials or repairing an actual identity/scope failure, without routinely running verification before every shortcut.

Command help supplies exact flags. The original `lark-doc` skill and references remain available through `lark-cli skills read lark-doc` for unfamiliar block syntax, detailed authoring profiles or resource workflows. Relative `@./file` content paths resolve from the CLI working directory; `-` reads stdin. File/stdin input avoids multiline shell quoting damage. Literal leading `@` uses `@@`; `--pattern` does not read files.

Reading and editing:

`docs +search --query ... --as user` searches documents, Wiki and spreadsheets with optional JSON filters and continuation. Folder tokens scope document search; space IDs scope Wiki search; do not combine both. Default page size is 15, capped at 20. Preserve `has_more` and `page_token`; multiple name matches are not a unique resource identity.

- `docs +fetch --doc URL_OR_TOKEN` supports Docx/Wiki and selection links containing `#share-...`. XML is the default native representation. `--detail simple` is for reading; `with-ids` exposes block addresses; `full` supplies IDs, styles and edit/reference metadata. Markdown and IM Markdown are explicit conversions; full edit metadata belongs to XML. IM Markdown is for subsequent message use, not document authoring.
- Choose a useful scope: outline for headings (`--max-depth` limits heading levels), section anchored by `--start-block-id`, range with at least a start or end, or keyword with `--keyword`. Keyword matching supports substring/normalization and regex fallback; `|` separates alternatives. End `-1` reaches the document end. Sibling context surrounds selected top-level blocks; container/table excerpts may ignore that context. Outside outline, depth `0` requests only the block and `-1` is unlimited.
- Partial XML uses `<fragment>`; `<excerpt top-block-id="..." parent-block-path="...">` identifies a container/table slice. Do not mistake excerpts for complete blocks. Table keyword reads can omit unmatched rows; a range whose endpoints both name the table retrieves the whole table. Use the returned native IDs for subsequent addressing; structural changes can invalidate earlier addresses.
- `document.content` and `document.reference_map` belong together. Comments are returned in the `comments` sidecar, including with Markdown, which lacks inline comment anchors. `comments.tips.data` can signal comment truncation; document `tips` can signal replay limitations or degraded dependencies. Independent comments and complete comment pagination use Drive.
- `docs +update --doc ... --command str_replace --pattern ... --content ...` replaces simple inline text within rich content. It does not replace resources; empty replacement content explicitly deletes the match. Use block replacement for paragraphs, multiline content or multiple blocks. Preserve native formatting and resource identities when editing nearby text.
- Block operations are `block_replace`, `block_delete`, `block_insert_after`, `block_copy_insert_after` and `block_move_after`. Replace/delete address a native ID, comma-separated IDs, or an inclusive `--start-block-id`/`--end-block-id` sibling range; ranges require both endpoints and cannot also use `--block-id`. Do not reverse or span unrelated containers. Copy/move need `--src-block-ids` and a destination `--block-id`; append inserts at the end. Source copy supports ordinary blocks plus image/file/whiteboard/sheet/chat-card/sub-page-list resources, but not every resource type. Moving existing blocks preserves their native addressing intent.
- `overwrite` deliberately replaces the entire body and can rebuild block IDs or lose comments and other non-body objects. Do not use it to emulate a local edit when those objects must remain. If preservation requirements conflict with overwrite, explain the limitation and resolve it. Preserve structured reference maps for replay. After warnings, partial success or a revision conflict, inspect the actual latest content and stop repeated overwrites when verification fails. A base revision field is not evidence of external concurrency protection.

Authoring:

Semantic authoring uses XML by default. Markdown is appropriate when explicitly requested or faithfully importing supplied Markdown. Do not mix two complete document formats; supported XML extensions can occur inside Markdown. New authoring considers the reader's task, genre/content contract, facts and available meaningful visuals, then records a Presentation Decision and creates a draft with `docs +script --command init-draft --presentation-decision ...`. The decision describes audience, reader task, genre/adapter, presentation mode, word-count goals and planned blocks. The returned `draft_path` is reserved but the XML file does not yet exist. Write the candidate there, then `+script --command parse --content @./...` checks the profile/resources. `ok` means execution succeeded; `data.assessment.status` and diagnostics report quality checks. Fix local defects rather than rebuilding a valid draft wholesale. Parse supports local XML or online `--doc`, not Markdown. Importing complete user-supplied content or creating a title-only document can use `+create` directly.

`docs +create` accepts content/title, XML or Markdown, and either a parent folder/wiki token or a parent position such as `my_library`. A nonempty title can create a title-only document. Inspect returned document ID/URL, revision, new block IDs/resource tokens and warnings. New authoring should verify its delivered content; direct import preserves the supplied representation.

XML uses quoted attributes and normal block flow. Use one document title, continuous heading levels, paragraphs, native inline bold/emphasis/underline/deletion/links, nested lists inside list items, checkboxes, tables with paragraph content in cells, code inside `<pre><code>`, LaTeX, grid columns whose ratios sum to one, and supported callouts/resources. Callouts accept text/list/checkbox content, not arbitrary tables, images, grids, code or resources. Escape text `<`, `>`, `&` rather than escaping XML tags. Mentions require real native IDs, not guessed names. Preserve supported extended blocks and their reference maps instead of flattening unfamiliar content. Consult the retained XML references for HTML5, embeds, colors, merged cells and uncommon blocks.

Markdown exports already contain meaningful escapes; do not remove them before writing or matching. Escape literal backslashes, backticks, emphasis/link/math/deletion markers and `<`, plus headings/list/quote markers at line starts and `|` within table cells. Code spans/blocks are literal. Prefer relative files/stdin or literal shell quoting over interpolating multiline Markdown into a shell.

Resources and routing:

- `+media-insert` appends a local image/file; `+media-upload` uploads to an explicit supported parent type/node and returns a file token; the insertion wrapper orchestrates block creation and token binding. Use exact block content insertion when another location is required. Keep the user's specified source: clipboard means `--from-clipboard`, disk means `--file`; these are exclusive. Empty clipboard is a real failure: explain it and obtain a replacement image/path, never guess a recent file. Clipboard is built in on macOS/Windows; Linux needs xclip, wl-paste or xsel. Large files use multipart upload. Image alignment, caption and display dimensions are optional; PNG/JPEG/GIF can infer the missing dimension, other formats may need both.
- Local XML `<img path="@./...">` and `<source path="@./...">` orchestrate upload/binding; existing image/file tokens preserve resource references. Public remote images must satisfy the CLI's URL, content-type and size checks. Do not bypass rejected private/loopback/link-local URLs, userinfo or redirect validation. Use authorized local input when a remote source cannot be fetched safely.
- `+media-preview --token ... --output ...` previews image/file/comment media. Explicit downloads use `+media-download`; whiteboards require `--type whiteboard`, not preview. Download extensions can be inferred from response content type. Export permission failures may allow preview; rate limits call for delayed backoff, not immediate retry loops.
- Covers are separate from body image blocks: use `+resource-download`, `+resource-update` or `+resource-delete --type cover`. Update accepts one of file, clipboard or public HTTPS URL and optional offsets; existing output files require explicit overwrite. An already-empty cover clear is a successful no-op.
- Embedded Sheets/Base data belongs to those domains. Meeting transcript embeds route to meeting/note commands. Synced references need their source document/block. Reuse an existing whiteboard token when updating; do not create a blank replacement. `whiteboard +update` supplies raw/Mermaid/PlantUML/SVG content. Existing mindnotes use mindnote operations; new diagram-style mindnotes follow the whiteboard workflow.
- Drive owns search/navigation, import/export, permissions, independent comments and actual file copy. Do not copy a document by fetching and recreating its body when preserving original resource semantics matters.

History uses `+history-list` with bounded pages and continuations, then `+history-revert --history-version-id ...` and `+history-revert-status --task-id ...`. A history version ID differs from a document revision. Resolve duplicate revision candidates with edit times; ambiguous candidates need a choice. Search all pages before declaring a requested revision absent, including adjacent candidates across page boundaries. For a time target choose the latest entry not later than it, unless the user explicitly asks for the nearest. Revert status `running` requires polling; only `done` is successful, while `partial_failed`/`failed` require reporting affected blocks. Permission/network errors do not mean a version is absent. Revision-based body-restore fallback requires full matching revision/document reads, removal of old block IDs and one bounded overwrite against the observed current revision; identical revisions require no overwrite. Its comment/identity-loss limitations still apply.
