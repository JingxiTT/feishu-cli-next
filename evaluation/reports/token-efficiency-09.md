# Token efficiency 09: harder Docs workloads

Final protocol for the implemented `docs-hard-v1` cohort. Provider execution requires an immutable evaluator/candidate freeze, matching preparation evidence and independent readiness approval. The protocol and controls below make no measured token-saving claim; no condition-09 model calls have run during preparation.

Use three harder Docs tasks, original/full versus the improved candidate, with three fresh repetitions per task and arm: **18 serial model attempts**. This is the smallest useful comparison that separates rich-content interpretation, focused retrieval and multiple edits. Finish all 18 attempts; there is no performance-based early stop between these Docs tasks. Six additional unrelated functions and a size sweep are outside this condition.

This cohort differs from the fixed tasks in [condition 08](token-efficiency-08.md). Keep historical tasks, fixtures, results and costs unchanged. Do not pool their attempts, reuse their original baselines, or express cross-cohort differences as an improvement percentage. The new tasks test harder work; they do not establish that performance on the old tasks improved.

## Tasks and fixed inputs

All tasks use `section: docs` and the separate manifest `evaluation/tasks.docs-hard.json`. The fixture owner selected a single versioned factory, `evaluation/paired/docs_hard_v1.py`, keyed by `case_id`, with `scenario_section: docs-hard-v1`. Public answer schemas contain types and structure only, with closed objects suitable for the pinned provider. Expected values, native state and verifier hashes stay evaluator-owned. Prompts name the resource and requested outcome, without prescribing a command, discovery sequence or candidate-only workflow.

| Task ID | Concrete workload | Independent outcome checks |
| --- | --- | --- |
| `docs-hard-rich-read` | Read a small release-checklist section containing a native table and an ordered list with nested items. Return the requested SKU row, preserving its empty cell, Unicode and numeric-looking text, plus the top-level steps and nested children in order, with the requested table/list block references. | Exact row/column associations, text values, list order, parent/child membership and requested native references. Signed reads must actually expose the relevant native content and relationships. Whole document state, metadata and permissions remain unchanged. |
| `docs-hard-focused-read` | Find the final approval code and release lane in a uniquely named project section of a deterministic multi-project document, with varied readiness facts and plausible archived approval codes/lanes elsewhere. Return the facts and their native evidence references. | Correct target-section association and exact facts/references, backed by actual returned content. No mutation or unrelated state change. The frozen environment records exact bytes, block count and input hash; this is one concrete retrieval workload, not scaling evidence. |
| `docs-hard-multi-edit` | Make three unique wording replacements: two within one paragraph and one in another. Include an edit within plain text, an edit within a bold run, and an edit to a hyperlink label. Keep unrelated native table/list/media content. Return the document ID and both complete changed paragraph texts in document order; current edited block IDs remain verifier evidence rather than required answer fields. | All three requested text changes, native marks and original link destinations, and every unrelated block/resource/parent/order/metadata value. Verify the signed mutation chain and final native state; authoritative mutation content or readback can provide proof when sufficient. |

The focused source contains twelve distinct project records with fourteen operational paragraphs each: the current Orion release, an earlier Orion archive and ten other named projects. Their approval codes and release lanes are plausible distractors. It is a concrete larger-document retrieval case, not a repeated-padding or minimum-page-count target. Native pagination is separately controlled with pages of 100 and 81 blocks. Every arm/repetition receives the same deterministic input.

The rich-read task measures whether the agent can use the readable representation without losing table/list meaning. It does not grade exact Markdown whitespace or require the candidate's rendering. Check readable table/list rendering separately through deterministic product controls. Original XML, native JSON and a local transformation remain valid ways to answer the task.

Focused reads must be optional strategies. Both arms may use scoped/keyword/section reads, individual blocks, complete block pagination, or a full fetch followed by local selection. A full read is not a verifier failure and incurs its actual token cost. Do not disclose the answer in an outline, metadata field or synthetic list of returned block IDs when the corresponding native response does not provide it.

For multiple edits, make each replacement unambiguous inside one uniform native style span. Verify native text and marks, not a visual Markdown imitation. Plain replacement text does not inherit missing bold/link marks merely because some characters resemble the old span. Preserve actual unrelated resource identities; do not require invented inline GUIDs, unchanged run segmentation, or an unchanged edited paragraph ID when a supported native replacement rebuilds it. Native state may show the requested edits in sequence, but an unrelated mutation must not become acceptable merely because it was later restored. Do not claim that a multi-request edit is atomic or that native revision parameters enforce compare-and-swap.

## Fair comparison and accounting

Pin native Codex CLI `0.153.4`, `gpt-5.6-luna`, reasoning `medium`, the candidate and original binaries, evaluator archive, API catalog, complete guidance trees, task manifest and protocol hashes. Keep the original reference revision and full `lark-doc` entry bytes unchanged. Every original baseline is fresh. Both arms receive the same task, initial native state, tools, 180-second agent budget and 210-second outer budget.

Retain the shared filesystem-only skill delivery and corrected ambient-skill suppression from condition 08. Both arms are instructed to read their selected skill completely inside the measured loop. Copying files is preparation; reading guidance by the agent remains measured. Do not pre-read either skill outside that accounting, prescribe an always-run help sequence, or apply per-arm delivery overrides. Complete skill reading is a prompt requirement, not a new hidden success predicate.

Use the existing balanced schedule with seed `20260909`, preserving its recorded order, with a fresh context for every attempt. Run only one provider stream. Complete the scheduled cohort despite individual failures. Stop further starts only for demonstrated shared fixture/runner defects, unavailable provider/accounting, or an authorization issue; retain completed and active-attempt costs and mark unstarted slots separately. Correct a defective fixture under a new version before any balanced replacement condition. Never replace an individual inconvenient result.

Each of the three Docs tasks independently requires **strictly more than 50% fewer all-attempt provider tokens per verified success** than original/full, with no observed success regression. Include failures, recovery and guidance reads. With positive success counts and complete accounting, compare integer totals using:

`2 * next_total_tokens * original_successes < original_total_tokens * next_successes`

Exactly 50% fails. Any unknown usage, inconclusive outcome or zero verified successes makes that task's token comparison unavailable. Also require `next_successes >= original_successes` for the equal-sized arms. A known success regression fails the combined task gate even when its cost comparison is unavailable. No pooled percentage, matched-success subset or mean cost per attempt can satisfy an individual gate.

Report actual input and output tokens, count cached input once in full, and keep partial known spend as a lower bound. Report all-attempt tokens per verified success, success counts, unknown/inconclusive counts and attempt distributions per task/arm. Matched successes and mean attempt costs are secondary. API calls include actual agent-side signed fixture requests and bootstrap; evaluator-only probes are separate. Command counts and bounded error labels are diagnostics, not per-command token attribution. Three repetitions provide point estimates, not statistical parity or stable population savings.

## Bounded native and classification limits

Table/cell native shapes reuse the previously native-checked paired Markdown contract. Ordered/bullet fields follow `oapi-sdk-go` v3.7.2 and existing XML list-converter tests; these fixture projections are source-backed synthetic representations, not newly observed live rendering. Full XML and the controlled focused/native routes are supported. A scoped XML selection that omits required descendants of a container is explicitly unsupported; no general native tree editing or history engine is invented. Raw text without native references and XML without IDs cannot alone prove the required block references. Merely seeing a child ID does not prove its empty cell or table content was returned.

Only `docs-hard-v1` adds the reviewed known-failure classification rule: a definitively wrong final answer or an independently signed preservation/final-format failure remains a failed verification even if another request is unsupported. Missing read/completion proof with an otherwise correct answer can remain inconclusive. Correct answers do not become successes without the normal proof checks. Final native marks use the same criterion with or without an unsupported request; repaired intermediate marks on edited targets do not introduce a new hidden failure criterion. All unrelated state must remain preserved through the mutation chain. Historical scenario classification is unchanged.

Invalid/foreign requests and invalid signatures remain distinct from documented but unmodeled strategies. Missing diagnostics do not establish that a route was valid or identify a product failure. All results and costs remain in the report; do not turn fixture coverage gaps into live reliability claims.

Before provider dispatch, archive the final protocol, factory/data dependencies, report/launcher scripts and guidance; check all three closed provider schemas and registry loading; run preparation-only against the exact binaries; and obtain independent readiness approval for those hashes. The reporting boundary has seven no-model arithmetic controls, including strictly above/exactly/below 50%, unavailable costs/coverage, and known success regression. Exactly 50% is not rounded into a pass; unknown/inconclusive token scores stay unavailable while a known success regression still fails the combined gate. No paid probe, additional model arm, size sweep, performance early-stop between these tasks or unconditional follow-up cohort is part of this condition.
